# 台账 2026-11-12（接续 `art/ledger-20261110.md` 的 §721）

## §722 路线 8 回归：镜像扩到 `/system/bin` 后 0 字节占位砸死 adb，`exec /system/bin/sh: Permission denied` 直到重启

机主原话：「这tmproot app怎么更新拆东墙补西墙呢? 一更新其他版本就root不了了」→ 复述澄清：
「我之前是在7.12.15维护的 声明支持1.15.1 7.12.15 8.19.16 但现在切到了8.19.16发现原本旧版本
就适配过的这个版本现在root不了了」。

### 现象（8.19.16 / 3.18.71-perf-g8a8c60dd，SELinux 开机 Enforcing）
- 点「提权」后：内核写全部成功（`getenforce` 变 Permissive，avc 日志 `permissive=1`），
  **但 adb 当场死亡**——`adb shell` 任何命令都报 `exec '/system/bin/sh' failed: Permission
  denied`，拔插线/换 USB 模式（6007↔6003）都救不回，只有重启恢复。
- 应用日志一行定案：`mirror su paths: MIRROR8 ok: /system/bin|mirror8.sh[40]:
  /system/bin/toybox: can't execute: Permission denied|...` —— 第一个 stage_dir
  `/system/bin` 报 ok，**随后**镜像内的 `$T`（toybox）就 exec 不动了。

### 根因
`9af7db9`（路线 7 名字闸 commit，净 1423 行）在 `Chain.openSuName8` 的 `mirror8.sh` 里
把 `stage_dir /system/bin`、`stage_dir /system/xbin` 两个目标加进了路线 8 共用的镜像逻辑：

1. `stage_dir` 先 `: > "$r/$n"` 建 **0 字节占位**，再逐个 `mount --bind` 盖回原文件，
   失败则 `cp -p` 兜底——两段都是 `2>/dev/null` **静默吞错**；
2. 只要有一个文件 bind 和 cp 双双失败，镜像里就留一个 0 字节洞，而循环后的
   **整树 bind `$r → //system/bin`（vivo 挂载钩子绕行）照常执行**，`MIRROR8 ok` 只代表
   最终目录 bind 成功，不代表树是完整的；
3. 机主原话确认 ROM 无偏差（「不会有误差」），排除了地址漂移；实测
   `adb pull /system/bin/sh` = **0 字节**，实锤洞在 `sh` 这个条目上（symlink 条目的
   bind+cp 双失败，`sh`/`toybox` 同为高危）；
4. 挂载来自内核域（modprobe payload / root 通道）的**初始命名空间**，adbd 一并看到坏
   覆盖层 → 全系统 exec 穿过 `/system/bin` 都是 EACCES → adb 死，重启清挂载恢复。

路线 7 自己没事的原因：它的投递已换成 nsmbind（同 commit 明言「placeholders do not show
up as 0-byte /sbin entries」，就是修 0 字节占位问题），而路线 8 用的还是旧式逐文件 bind。
**这就是"拆东墙补西墙"：给路线 7 修占位坑的同时，把一个更老的坑送给了路线 8。**
1.9.41 之前所有 8.19.16 版本的镜像都是 `/sbin`-only（注释「an old build's /sbin-only
mirror」为证），adb 不经过 `/sbin`，所以从没炸过。

### 改动（Chain.java openSuName8，v1.9.42 / versionCode 61）
- 镜像回退 **`/sbin`-only**：删掉 `stage_dir /system/bin`、`stage_dir /system/xbin`，
  标记检查简化为 `[ -f /sbin/.r8mirror3 ]`，见证行只看 `/sbin/su`。8.1 的 app PATH 含
  `/sbin`，旧版本已证明足够投递 `su`。
- **洞守卫**：目录条目 bind 失败、文件条目 bind+cp 双失败时 `echo "HOLE8: $d/$n";
  return 1` —— stage_dir 在**整树 bind 之前**中止，带洞的树永远到不了目标路径。
  宁可不出 su，绝不再砸 `/system/bin`。
- 构建按惯例明写 `SKIP_GATE=1`：本次只改 Java 链路，未动任何内核常量。

### 验证（真机 8.19.16）
- `adb install -r` 覆盖装 1.9.42（同证书，授权名单保留；vivo 两段确认弹窗人工点掉）；
- 重启后点「提权」：**adb 存活**（`exec-ok`）、`getenforce` = Permissive、
  `su -v`/`su -V` = MAGISKSU/30700，应用自报「root已就绪 adb连接正常」；
- `su -c id` = `REFUSED no token` 为授权闸正常行为（shell 未入名单），非故障。

## §723 hpgain 移植到 3.18.71：kallsyms 离线恢复取 `wcd_hph_gain`，写入原语换 route-8 布局，见证串对齐 `CLOBBER OK`

机主原话：「app里点击设置-音频-跟随1.15.1提示没打到」→ 批准移植（「好的，执行吧」）。
v1.9.43 只带了常量没带写入参数，装机后仍失败；三轮定位才真正打通（1.9.44 原语、1.9.45 见证串）。

### 根因一：常量缺失 → kallsyms 离线恢复（v1.9.43）
- hpgain 臂的常量集只有路线 7（`3.18.31`），在 8.19.16（`3.18.71-perf-g8a8c60dd`）上 REFUSE。
- `wcd_hph_gain` 是数据符号，没有任何 gate 站点引用它，pgdalias 推不出来；本机无 8.1 的
  fw/Image，实时 `/proc/kallsyms` 又因 `kptr_restrict=2` 读不到地址（root 也一样），只能从
  **9008 备份的 boot.bin 解出的 8.1 内核 Image 离线恢复** kallsyms → `art/kallsyms-8-real.txt`。
- 恢复要点（文件头注释有完整记录）：addresses[] @0xf81200（96829 条，VA = foff +
  0xffffffc000080000）；names/markers/tokens 各段定位靠 `num_syms` 附近零垫。
  三个锚：`modprobe_path` 字面量 == MODPROBE8_ADDR（0xffffffc001815540）、名称集合与设备
  dump 全等、首名 `_text`。
- **vivo quirk（两版内核共有）**：names blob 把类型字母并入名字首 token（`t`efi_head、
  `D`modprobe_path、`d`wcd_hph_gain），必须按首字符切分；设备 dump 大输出经 su 通道帧
  重组**乱序**，只能当集合参考不能当顺序参考。排错记录：计数校验、`vals[0]==_text` 锚定、
  names/token 解码各失败过一轮，都是这个 quirk 的变体。
- 恢复结果：`wcd_hph_gain` = 0xffffffc001963ec0，邻居 `soc_codec_dev_tasha` =
  0xffffffc001963ec8（span 8，4 字节写入不越界）。`selinux_enforcing`/`init_cred`/
  `commit_creds` 被 vivo 剥除（MISSING，与本任务无关）。
- `gate_constants.py` 加 `8.19.16` profile（kall-only，无 ALIAS_DESC_HEX 的 DESC 跳过），
  单独验证 4/4 ok。本机缺 fw/Image 全量 gate 跑不了，构建按惯例 `SKIP_GATE=1`。

### 根因二：写入原语是 6.0.1/7 专属，3.18.71 上 arm 步骤自己就死（v1.9.44）
- 常量带上后 CLI 实测：`drain 0: reply already eaten (round unusable)` —— clobber 的
  `arm_pending_tx()`（保持待处理事务跨 drain）在这版内核上拿不到「BR_TRANSACTION_COMPLETE
  已清而 BR_REPLY 未吃」的窗口；且 freed binder_thread 布局也不同（我们是 0x128 +
  task_list@0x50 → WQI=4；3.18.71 是 V20 形，wait 条目落在 25 元素数组的 iov[9..11]）。
- 修法：把路线 8 已真机验证的原语（`tools/esc8.c` 的 `w8_try_once`/`w8_write`，首发 5/5）
  移植进 clobber.c（`r8_init`/`r8_try_once`/`r8_write`，仅 `#ifndef ESC_LIB`——libesc.so
  里这条路走 esc8 自己的升级链，broot7 的字节不许重掷）。hpgain 臂按 osrelease 分派：
  `HPGAIN7_RELEASE` → 原 route-7 路径；`HPGAIN8_RELEASE` → route-8（无 arm_pending_tx，
  32 字节 payload 重写 iov[10].len 与 iov[11]，成功判据 `readv == FILL8+PAYLOAD8+datalen`
  = 65573）；未知仍 REFUSE。
- 真机验证：v1.9.44 首测 try1 即命中（65573）；按 app 同款调用复测 try1/try2 落空、
  **try3 命中**——载具是概率性的，与 esc8 的实测一致，重试节奏（120ms，上限 4 次）有效。

### 根因三：见证串不匹配（v1.9.45）
- 机主：「点击还是提示增益没打到」。写入其实已经落地——`hpGainLanded()` 只认
  `indexOf("CLOBBER OK")`，而 route-8 路径打印的是新造的 `*** landed ***`。
- 修法一行：route-8 命中改打同款 `*** CLOBBER OK ***`。教训：**成功判定字符串是接口**，
  新路径必须带旧见证，不然工具链每一段都成功、端到端却报失败。

### 验证与版本
- v1.9.45（versionCode 64）装机，`/data/local/tmp/clobber 40 hpgain 601 4 0`（app 同款）
  try1 即 `*** CLOBBER OK ***`；601 臂值 {4,1,1,1} 已入 `wcd_hph_gain`，生效待下一次耳机
  通路使能。
- vivo 安装器 `Failure [-200]` 静默拒绝再现过（1.9.43 时三连拒无弹窗，第四次重试直接
  Success），结论不变：重试即可。
