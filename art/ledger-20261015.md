### 200. 「MT 管理器还是看不了 /data/*」＝两条独立原因（DAC＋它没去 exec su），顺着这条挖出**我们自己的交互档 su 缺陷**（peer 通道不剥换行 ⇒ 哨兵 `"-\n"` 比较不上）

- 现场读数（一条一条量的，不是推的）：
  1. MT ＝ **`bin.mt.plus`，uid 10132**。`pm list packages | grep -i mtxx` 找不到它（包名里没有 `mt.` 域那种写法）⇒ 改从 `/data/system/packages.list` 现读 uid→包名才对上。
  2. 它**已经在名单里**（`grants.txt` = 10022 10142 10028 10132）——是用户在新界面上拨的，说明"拨胶囊即写名单"这条路真人走通了。
  3. 它自报域 `u:r:untrusted_app:s0:c512,c768` ＝ 点位集里的 type 627（MLS 类别不参与按 type 的豁免，见 §196 那条）。
  4. 它自己的 `/proc/<pid>/environ` 里 **`PATH=/sbin:/vendor/bin:/system/sbin:/system/bin:/system/xbin`** ⇒ `/sbin` 排第一，而 `/sbin/su` 是 0755 root ⇒ 它 `exec("su")` 一定命中我们的客户端。
  5. 它的进程启动时刻 00:54:27 ＝ **在授权之后**（我为了量它才 monkey 起来的）⇒ 排除"缓存了授权前的无 root 判定"这一档。
  6. **可是 `sud` 的审计日志里 10132 零条**（只有 10142 管理端和 2000 shell）⇒ MT 从头到尾没 exec 过 su。
  7. `/data` 与 `/data/data` 都是 **`drwxrwx--x system:system`（0771）** ⇒ 非 root、非 system 组的 uid 只有 `x` 没有 `r`，**列目录这一步必拒**。这是 **DAC**，`permissive_map`（MAC）一点都碰不到它。
  ⇒ 对用户那句话的准确回答：**闸、点位、名单、PATH、su 文件名全到位；卡的是 MT 自己没去调 su（它的 ROOT 开关），而只要不 root，`/data` 的 DAC 就永远不给它列。** 这一步要人配合：在 MT 里开 ROOT（或首次进受限目录时接受弹窗），我再从审计日志认那行 `allow uid=10132`。
- ★顺着"万一 MT 用的是交互档"去量，撞出**一枚我们这边的真缺陷**：`su -c id` 通，但**裸 `su` / `su -` 回 `sh: sh: -\n: unknown option`、`@SUD_EXIT=1`**。
  根因＝**两条通道各自解析同一行**：TCP 走 `read_one_line()`（遇 `\n` 即停、不存），peer 走 `recv_cred_line()`（`recvmsg` 后只补 `line[n]=0`，**换行留在串里**）
  ⇒ 交互哨兵到守护进程时是 `"-\n"`，`strcmp(cmd,"-")` 不等 ⇒ 掉进 `sh -c "-\n"`。同一枚缺陷的第二张脸：`MOUNT <path> bin` 里 `!strcmp(sp,"bin")` 在 peer 路上也永远不等。
  修法＝`recv_cred_line()` 补一行 `line[strcspn(line, "\r\n")] = 0;`，让两条通道对齐。
  验收＝机上 `files/sud` md5 `ce7b8c2d…` → `14d4f07e…`（证人：`Chain.java:53` 每次提权都从 asset 重拷，所以换 APK＋重启即换守护进程）；
  `printf "id\nls /data|wc -l\n" | su` → `uid=0(root) … context=u:r:qti_init_shell:s0` ＋ `48`；`su -` 同；`su -c id` 不回归；`verify_approot.sh` **pass=8 fail=0**。
  注：交互档仍会把 `@SUD_EXIT=0` 这行尾巴吐给调用方（只有 `-c` 档剥掉），它出现在会话最末尾，对 root app 无害 ⇒ 本轮不动。
- 同轮三个读数坑（都是我自己的）：① `for a in …; do timeout 6 su $a | head -3; echo rc=$?; done` 里 **rc 是 `head` 的**（管道吞退出码，第 N 次犯）；
  ② 主机侧 `grep -v` 撞上设备输出里的 NUL ⇒ 只回一句"匹配到二进制文件"，我把"设备没输出"错读成"脚本没跑"（设备输出一律先 `tr -d '\000'`）；
  ③ 设备 `sh` 里 `"\0"` 不是 NUL（要 `'\000'`），而 `${p:/proc\/}` 这种带转义的替换 mksh 直接 `bad substitution`。

### 201. 「看到了」的机制确认：MT 用的正是**交互档 `SU 0 -`**（＝我刚修那条），拿到 root 后自己养 root helper；顺带量出两条这套 su 的性质

- 证据链（全部现读）：
  1. `sud.stage`：`peer: connected to @trq10132.4550` → **`peer request uid=10132 pid=4550: SU 0 -`** ⇒ MT 发的就是交互哨兵（`suc.c` 里 `cmd==NULL` 才发 `-`）。
     这条路在 §200 的修复之前是**必坏**的（掉进 `sh -c "-\n"`），所以"修完就好使"是因果闭合，不是巧合。
  2. 进程树：root `sh` **pid=4556 还活着**（紧跟在 4550 之后），它的两个子 helper **`mtio` pid 4599/4617 ＝ uid 0 / gid 0 / 域 `u:r:qti_init_shell:s0`**，
     被 init 收养（daemon 化）。⇒ MT 的"看得见 /data"不是它自己 uid 变大了，而是**它把 root 侧 helper 常驻起来代它列目录**。
  3. MT 主进程 4497 仍是 `u:r:untrusted_app:s0:c512,c768` uid 10132（授权前后没变），名单/PATH/域三件事与 §200 的读数一致。
- ★由此量出**两条该写进设计说明的性质**（都不是 bug，但会影响验收和"撤销"的语义）：
  1. **撤销只挡新请求，掐不掉已经开着的会话。** `verify_approot` 的 D 项验的是"下一次请求被拒"，而 MT 这类 app 会把交互 root 会话**长期持有**
     ⇒ 拨回灰色后，MT 的 `mtio`（uid 0）照旧在跑。要真做到"撤销即断"，得让守护进程按 uid 记账活动会话并在撤销时发 SIGHUP（未做）。
  2. **交互档的 `allow` 行要等会话结束才落账**（`sud.c` 里 `su_log("allow …")` 在 `waitpid()` 之后）
     ⇒ 运行期的高权限会话在审计里是**隐身**的：`grep uid=10132 sud.log` 读到 0 条，而 root 进程明明在。
     判"谁现在有 root"只能扫进程树（`tools/rootholders.sh`），不能只看日志。
- 顺带一枚待查：进程树里还有 **10 枚 uid=0 的 `sh`，cmdline 为空＝僵尸**（pid 4144/4158/4220/4223/4296/4302/4366/4370/4394/4426）
  ⇒ 有连接 handler 没在 `wait()` 自己那枚子进程（或子进程被转成了别人收养后死掉），会话在泄漏进程槽；本轮只记录，未修。
- ★我自己的一处读数坑（差点把结论写反）：第一版 `rootholders.sh` 用 `tr -s ' '` 切 `/proc/*/status` —— 那文件是 **TAB 分隔**，
  挤空格不动 TAB ⇒ `Uid` 字段取成空 ⇒ **所有 root 进程被静默跳过**，我因此一度得出"没有 root shell 活着"。
  改成 `tr '\011' ' '` 后同一发就数出 13 枚。⇒ 又一次"整齐的空结果先怀疑我的编码"（同族见 §200 的 NUL/管道退出码两条）。

### 202. 三件一起做了：**决策时落账 ＋ 撤销掐活会话 ＝ 不泄漏僵尸**（`sweep_sessions`），新尺 `verify_sweep.py` 8/8，`verify_approot` 仍 8/8

- 实现（全在 `tools/sud.c`）：
  - 会话台账用**文件**：`SESSDIR=/data/local/tmp/.sud/sess/<子进程 pid>`，内容 `uid pid tries`。
    原因很实在：fork 出会话的那个连接 handler 和 accept 循环**不是同一个进程**，内存表扫不到。
  - `sweep_sessions()` 挂在主循环 `scan_peers()` 旁边（select 超时 0.5 s ⇒ 一拍最多 0.5 s）：
    ①`while (waitpid(-1, &st, WNOHANG) > 0)` 收**本进程**的孩子（`serve_tcp` 以前 fork 完根本不等 ⇒ 那 10 枚 root `sh` 僵尸就是这么来的）；
    ②逐个台账项 `kill(pid,0)`：没了就 unlink（handler 可能没来得及自清）；还在但 `!uid_allowed(uid)` 就**两拍制**收：先 `SIGHUP`（并把 tries 写回 1），下一拍仍活着补 `SIGKILL`。
    信号按**进程组**发（`kill(-pid,…)`），因为 `spawn_sh()` 里 `setsid()` 过，会话自成一组。
  - 审计：`open uid=… pid=… target=… <cmd>` 写在 `fork()` **之前**（判决一出口就落账）；原来的 `allow … code=N` 留在 `waitpid()` 之后不动
    —— 这样 `verify_approot` 的 E1/E2 那类按 `allow`/`deny` 起头的尺子一个字都不用改。
- 验收（`tools/verify_sweep.py`，8 项全绿）：`open … sleep 120` → 台账 `ENTRY=27356 2000 27356 0` → 撤名单 →
  `revoke … grant withdrawn, session hung up` → 下一拍 `revoke … session killed (survived SIGHUP)` → 收尾 `allow … code=137`（128＋9＝SIGKILL，**这行就是"确实是两拍制收的"的证人**）→ 台账 `REG=[]`、客户端返回、名单还原后 `su` 照旧。
  僵尸项：6 发会话前后 `root_zombies=0`（`root_live` 423→422 是别的进程自然波动）。
  `verify_approot.sh` 重跑 **pass=8 fail=0**（撤销语义、跨 uid 冒充闸、审计两行都没回归）。
- ★三处我自己造的坑（每一条都差点变成假结论）：
  1. **撤销动作跑在被撤的会话里**：第一版让 `su -c` 去改名单 ⇒ 名单一空，sweep 把**正在执行撤销的那条会话**掐了，`sleep 6; echo 2000 >>` 再没跑 ⇒ shell 授权丢失。
     救场靠 **12345 的 raw shell**（`tools/rsh.sh`：`adb forward` ＋ `/dev/tcp`，那条路不受名单闸管、也不登记会话）。
     ⇒ 通用口径：**测"撤销"的工装必须站在被撤能力之外的通道上**。
  2. `for f in …sess/*; do echo ENTRY=$(basename $f)` 在目录为空时把字面量 `*` 当成 pid ⇒ `kill -0 *` 永远失败 ⇒ `SESSION=GONE` 是**假绿**。
     ⇒ 判"死了没有"之前，先证明这把尺在"活着"那一态读得出真值（这次靠 2a 的 `ALIVE` 补上了）。
  3. `nohup sh x.sh >/dev/null 2>&1 &` 在 `adb shell` 里**不脱离控制终端** ⇒ 整条命令挂着 180 s 不返回（后台任务超时被停）。
     改用宿主侧 `Popen(['adb','shell','su -c "sleep 120"'])`：会话照样注册，还能用 `holder.poll()` 当"客户端回来了没有"的证人。
- 顺带一条真机事实（以前没量到）：这轮 `adb reboot` 后开机链**第一次没把名字闸打上**（`sugate: rc=-1 … rounds=24 rc=0`＝写原语那发没落位），
  而链子的其余部分全成（`attributed by token -> uid=10142`、root 探针 `code=0`、`/sbin` 已挂）⇒ 在管理 app 里点一下"提权"，20 s 后 `su -c id -u` 就 0 了。
  ⇒ "开机自动过闸"是**尽力而为**，不是必然；失败时的重试入口就是那个按钮（`EscService` 的 job 还会再来一次，`latency=3600000`）。

### 203. snub 工作区那条"环境的坑"从源头修掉了：**SU 子进程继承调用方环境**；顺带修**交互档退出码永远 0**，并撞出一个开机时序坑

- 来龙去脉：snub（`/home/v/.local/project/snub`，Hail 的 fork，冻结应用）今天两发提交 `817a450`（API 23 启动/搜索闪退）、
  `810769a`（"让 root 下的 pm/am/appops 真的跑起来"）。机上"怠"＝`io.github.AlexIllinois2.snub` uid 10022，**已在我们的名单里**。
  他们记的坑：vivo 的 su 清空子进程环境 ⇒ app_process 系工具缺 `ANDROID_DATA` 在 libjavacore `initStorageMap` 里 SIGABRT；
  他们的解法是在每条命令前补 `export ANDROID_DATA=…`（`HShell.execute`）。用户问的是：**这个坑能不能从源头补**。
- ★源头修法（`tools/sud.c` 的 `import_caller_env()`）：读 **`/proc/<调用方 pid>/environ`**（pid 是内核 `SCM_CREDENTIALS` 给的，不是自报），
  按 allow-list 挑 `ANDROID_ROOT/ASSETS/DATA/STORAGE/BOOTLOGO`、`EXTERNAL_STORAGE`、`ASEC_MOUNTPOINT`、`LOOP_MOUNTPOINT`、`TMPDIR`、`HOME` 十枚 `putenv`；
  读不到（token 归属那类 `cpid<=0`）再退回平台默认。**必须在 `setresuid` 之前做**（读别人 environ 要 root）。
  为什么不是"客户端把 env 打进协议"：请求行缓冲只有几百字节，而 `BOOTCLASSPATH` 一枚就 ~1 KB；从 `/proc` 现读既准（就是调用方那份）又不占协议。
- 实测（新尺 `tools/envtest.sh`）：修之前 `pm/am/appops/svc` 四把全 **rc=134**；**只补 `ANDROID_DATA` 就全 rc=0**（再多四枚没有额外收益 ⇒ 缺的就一枚）；
  修完 `su -c env` 里 `ANDROID_DATA=/data` 等五枚齐了。
- ★顺带撞出**交互档退出码永远是 0**：`printf 'exit 9\n' | su; echo $?` → 0（`-c` 路一直是对的：`exit 7`→7、`false`→1、强制 SIGABRT→134）。
  这正是 snub 提交里那句"而 su 仍返回 0"的来源——他们走的是"往 su 的 stdin 写命令"那条（`HShell.execute` 用 outputStream）。
  修法（`tools/suc.c` 的 `emit_flush()/emit_close()`）：流式档**扣住尾部 256 字节**，EOF 时从里头解出 `@SUD_EXIT=<n>` 并 `exit(n)`，
  顺带不再把 trailer 吐进调用方 stdout（`grep -c SUD_EXIT` → 0）。

### 211. 开机复验抓到交付口径的真窟窿：**map-only 六发不中→退回全局 Permissive 才拿到 root**，那类开机整台机器就没了 MAC；补一条"种成 map 就把 enforcing 翻回来"

- 把 §210 的 release APK（`1f1153f3`）装机跑一轮开机（`art/bootstats-release-verify.txt`：`device_up=35s root_at=60s landed_on_attempt=1 gate_ok=1 su_on_path=1`）——
  闸与 PATH 全绿，但**收尾读数 `getenforce` = Permissive**，`/sys/fs/selinux/enforce` 直接读也是 `0`，shell 域（uid 2000、`u:r:shell:s0`）同样读到 Permissive ⇒ **不是域豁免，是全局被关**。
- 全量开机日志把因果链摊开（同一 boot）：
  `escalate(mapOnly=1) attempt 1..5`：`step1 map rc=-2`（种 map 的那两发写空，enforce 仍 1）；
  `attempt 6`：`step1 map rc=0 enforce=1`（**map 种成了**）却 `step2 write modprobe_path rc=0` → `rc=-20`；
  ⇒ 应用打出 `map-only left us unrooted; falling back to the globally-permissive shape` → `escalate(mapOnly=0) attempt 2 rc=0`：
  `step1 write selinux_enforcing=0 rc=1` → `enforce reads 0` → 守护进程起来了。
  随后 `sugate ... PROVEN via enforce 0->1->0` 那句**不是把机器翻坏的元凶**——它只是照抄它进门前读到的 `was=0` 并原样写回。
- ★**判读修正**：`state after: ... enforce=Permissive` 这行历来被我当"链子跑完了"的顺带读数，其实它是**这一版交付的语义状态**。
  §208/§209 那几轮读到 Enforcing，是因为那几轮走的就是 map-only 正路（没触发兜底）；兜底这条路一直没被观测到过。
- 当场手验修法（root 走内核自己的接口）：`echo 1 > /sys/fs/selinux/enforce` →
  `cat /sys/fs/selinux/enforce`=1、shell 侧 `getenforce`=Enforcing、`su -c "id -u; getenforce; id -Z"` → **`0 / Enforcing / u:r:qti_init_shell:s0`**、`command -v su`=/sbin/su
  ⇒ 这一 boot 因为 attempt 6 已经把 map 种成，翻回 1 之后**第三方吃 root 的路一点没断**（就是 §188 以来一直宣称的 map-only 形状）。
- 落地成 v1.6（`Chain.java`）：
  ① `tryEscalate` 从原生气报里认出 `step1 map rc=0` 并记 `mapPlanted`；
  ② 只有 rooted && mapPlanted 才调 `restoreEnforcing()`：读 `getenforce`，Permissive 才翻 1，
     然后**用有风险的同一条 su 通道自证** `id -u; getenforce`；自证不回来就明写"唯一撤销是 adb reboot"；
  ③ 没种成 map 时**不翻**，直接打一行"permissive map never planted this boot -> staying globally permissive"
     （翻了对自己守护进程不利，也不诚实）。
- v1.6 装机开机复验（`art/bootstats-v16.txt`）：`device_up=40s root_at=30s landed_on_attempt=1 gate_ok=1 su_on_path=1`；
  这轮 `escalate(mapOnly=1) attempt 2` 就成了（`step1 map rc=0 enforce=1`，没走兜底），
  新代码路径的证人：`enforcing restore: not needed, Enforcing`；`sugate ... PROVEN via enforce 1->0->1`（两个方向都在 Enforcing 下证）；
  `getenforce`=Enforcing、`su -c id -u`=0、`/sbin/su` 在、`versionName=1.6` 被 PMS 认到。
- ★诚实标注：**"翻回 1"那一支在真机上还没被自动跑过**（v1.6 这一轮压根没触发兜底）。机制本身今天手验过（上面那条读数），
  但"兜底→自动翻回→自证"整串要等一次真·兜底开机才有证人。要主动撞它，就得连着刷几次"换包后第一次开机"（§208 那条负载假说）。
- ★交付口径按实测改写：**默认"Enforcing 下 root"；但 map-only 全轮空、只能靠全局兜底拿到 root 的那类开机，机器会在 v1.6 之前一直停在 Permissive**。
  v1.6 起，只要本轮 map 种成过就自动翻回；map 没种成则维持 Permissive 并明说（宁可不翻，也别把守护进程关死）。
