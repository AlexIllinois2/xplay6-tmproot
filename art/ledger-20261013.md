## 3. 缓解与"免费泄露"
- **无 KASLR**（arm64 随机基址 5.8+ 才有）；线性映射基 `0xffffff8000000000`（VA_BITS=39，已由泄露指针证实）
- `kptr_restrict` 生效：`/proc/kallsyms` 0444 但 90515 行地址全 0
- **`dmesg` 从 shell 直接可读**（且 avc granted/denied 全打在日志里）⇒ 开发期观测性极好，重启后开机段还能拿到 `Virtual kernel memory layout`
- **debugfs 已挂载且目录 world-readable**；`/sys/kernel/debug/binder/transactions` **0444 且直接吐真实内核指针**
  （实测 `buffer 37407308: ffffff8012380050`）；`ion/heaps/*`、`kgsl/kgsl-3d0/*`、`ipc_logging` 同可读
- `/proc/timer_list`、`/proc/sched_debug` 可读；ftrace 目录存在
- **没有任何 world-writable 的 debugfs/sysfs handler**（`find -perm -o=w` 空）；`/sys/module/*` 参数 0644

## 4. 方案设计（RAM-only，重启即复原）
1. **原语**：在 shell 可达驱动里拿「内核任意地址写」（addr+value 可控）。首选 kgsl(0666 RDWR)，次选 binder。
2. `selinux_enforcing = 0` → 全局 permissive（不落盘，重启还原）。
3. `modprobe_path = "/data/local/tmp/rootsh"`（`.data` 里可写的 char[]），随后 `execve` 一个坏 Magic 的文件
   → 内核 `call_modprobe` 以 **root** 执行我们的程序 ⇒ 拿到 root shell。
   ⇒ 这条收尾**不需要在内核态执行代码**（避开 PAN/UXN 与 ROP 的不确定性）；备选才是 `commit_creds(prepare_kernel_cred(0))` ROP。

## 9. 更正：第 7 节那条 "EFAULT 证明不查 f_mode" 是**假阳性**
`ION_IOC_MAGIC` 我按 `'O'` 写的（应为 `'I'`），那四个 cmd 全是**未识别命令**，EFAULT 来自收尾的 `copy_to_user(arg=NULL)`（反汇编里 `mov x0,#-0xe` 就是 -EFAULT），并没有走 ALLOC/FREE 分支。

## 11. ion 几何（全部来自本机二进制，不来自源码猜测）
- `ion_alloc` 里 `kmem_cache_alloc_trace(cache=1, gfp=0x80d0, size=0xc0)` ⇒ **ion_buffer 走 kmalloc-192**
- `ion_buffer_destroy` 暴露的字段偏移：`buffer->heap @ +0x28`、`buffer->size @ +0x40`、`int @ +0x78`(kmap_cnt)、`priv_virt @ +0x90`（喂 `vfree`）、`heap->ops @ +0x38`
- 3.18 `kref_put` 仍是裸 `atomic_dec_and_test`（无 refcount_t 饱和保护）⇒ 双 put 是真减 ⇒ 提前释放成立的前提在
- **待补**：`buffer->list/exp_info` 与 `buffer->vmas` 的偏移（`list_del` 是我们要的"写 8 字节"出口），下一轮从 `ion_buffer_destroy` 的 `__list_del_entry` 前置 ldr 对里取

## 12. 非内核兜底路：已被实测关闭
0666 的 root 服务 socket 全被本机 SELinux 拦住（`dmesg` 现读现证）：
`mpctl_socket(perfd)`/`iop_socket`/`thermal_socket` → `avc: denied { write } ... tclass=sock_file permissive=0`；`dumpstate/backuprestore/qseecomd/rmt_storage` 节点不存在。`logd` 能 connect 但 logd 不是 root 写原语。
⇒ 结论与用户判断一致：**只有内核这一条线**。

## 13. 目标链（当前设计，含两个已知待破的点）
1. 造 buffer 且 `SHARE/IMPORT` 复制出**第二个句柄** ⇒ `buffer->ref = 2`
2. 并发双 FREE 同一句柄 ⇒ ref 2→0 ⇒ 真对象被 `kfree`，而**第二句柄仍指着它**＝可控延迟触发
3. `add_key` 喷 kmalloc-192（`struct key`+payload 同块，payload 字节全可控）＝伪造 `ion_buffer`
4. 对第二句柄下 FREE ⇒ `kref_put` 在假对象上归零 ⇒ `ion_buffer_destroy(假)`：
   - **出口 A（写原语）**：假 `vmas` 让 `list_del` 把 `next` 写入 `prev+8`
     ⇒ 用来把 `selinux_enforcing(0xffffffc00189be74)` 写成 0：`prev=T-8`、`next=PAGE_OFFSET(0xffffffc000000000)`（低 32 位＝0 ⇒ int 变 0），附带写落在 `PAGE_OFFSET+8`（RAM 首 512KB，非内核映像区）
     ⇒ 同一次还能把 `modprobe_path+0x38` 种成"假 ops 表"地址（附带写落回自己 payload＝无害）
   - **出口 B（调用劫持）**：`heap->ops->free(heap, buffer)` ⇒ **以 x0=heap、x1=buffer 两个"我们选的 kernel 地址"调用任意内核函数**
     ⇒ 种好 ops 后令 `heap=modprobe_path`、`ops->free=strcpy` ⇒ `strcpy(modprobe_path, buffer)`
     ⚠ **未解**：`buffer+0` 必须是 `refcount=1`（`01 00 00 00`），`strcpy` 从 x1 首字节起拷 ⇒ 只会写进 1 个字节就撞上 NUL。
     候选破法（下一步逐个试）：① 找形如 `f(x0=dest, x1=src+8)` 的现成函数；② 让第二次竞态的假对象 `refcount` 落在别处（改由 `ion_handle_destroy` 路径触发而非 `kref_put`）；③ 放弃 modprobe_path，改用出口 B 直接 `commit_creds(假 cred)`（permissive 后 `cred->security` 可指现成 shell 的 sec 结构）；④ 出口 A 多轮 8 字节写把 `strcpy` 拷不出的路径分段写（需要值可控为 ASCII ⇒ 只在能附带写安全时才成立）
5. 触发：`execve` 一个坏 Magic 的文件 ⇒ kmod 以 **root** 跑 `/data/local/tmp/rootsh` ⇒ 起 frida-server，`adb forward` 连

## 15. 链路最终定形（把 §13 的"待破点"解掉了）
**出口 A＝写零**：假对象 `vmas.prev = T-8`、`vmas.next = K` ⇒ `list_del` 先做 `prev->next = next`
 ⇒ **把 K 写入 T**，再做 `next->prev = LIST_POISON2`（落在 `K+8`）。
 取 `K = PAGE_OFFSET = 0xffffffc000000000`（低 32 位＝0）⇒ `T = selinux_enforcing(0xffffffc00189be74)` 被写 **0** ⇒ 全局 permissive；附带写落在 `PAGE_OFFSET+8`（RAM 首 512KB，内核映像不在这里）⇒ 可容忍。
 若要写的"值"本身也得可控（如种 ops 指针），就取 `K = 我们 payload 的地址` ⇒ 附带写落在自己 payload ⇒ 完全无害 ✓
**出口 B＝任意调用**：`heap->ops->free(heap, buffer)` ⇒ **f(x0=heap, x1=buffer)，两个都是我们 payload 的地址**。
 取 `f = commit_creds`、`x0 = 假 cred`。原本卡在"heap+0x38 必须是 ops，而 cred+0x38 是敏感字段"——
 **实测 struct cred 0x38 = `struct user_struct *user`**（前面 8 个 uid/gid + secure + 三个 key_serial_t 推到 0x38），
 而 `commit_creds` 对 `new->user` 只做 `get_uid/atomic_inc` ⇒ 让 `user` 字段同时充当 **ops 表指针**，自洽无害 ✓✓✓
 假 cred 其余字段全可控：`usage=大`（永不释放）、uid/gid/euid/fsuid/suid=0、三个 key_serial=0、
 `group_info` = payload 里假 `group_info{usage 大, grouplist_count=0}`、`cap_*=~0`、
 `security` = payload 里假 `task_security_struct{magic='seli', sid/osid/tsid/nstid = 1(kernel)}` ⇒ 走真实 sid，审计/查表都不炸。
**顺序问题**（list_del 与 ops->free 谁先）：若 free 在前、list_del 在后，就**跑两发竞态**（第一发写 permissive，第二发 commit_creds），代价只是重试次数。
**为什么不需要 modprobe_path／ROP／PAN 讨论**：出口 B 用现成的 `commit_creds` 单调用即可拿 uid0＋cap＋sid，不需要在内核里执行我们构造的代码，也不需要栈 pivot。

## 16. 下一步实施顺序（每步都有独立判据）

## 17. ★链的更正与定形（读源码后：真正可喷的对象是 handle，且全部指针可以指向用户态）
命中率为 0 的**根因不是窗口窄**，是我拿错了引用：`ion_import_dma_buf` 对同 client 是**幂等**的（源码：`ion_handle_lookup` 命中就 `ion_handle_get` 复用）⇒ 没造出第二句柄。

真实引用算术（本机源码逐行核对）：`ioctl(FREE)` = `get_by_id`(+1) → `ion_free`(validate 后 −1) → `ion_handle_put`(−1)，净 −1；
初始 `ref=1` ⇒ **两个线程都在 `get_by_id` 里拿到引用**时，4 次 put 只配得上 3 次引用 ⇒
`ion_handle_destroy` 跑完后**仍有多余的 put 落在已 `kfree` 的 handle 上**（3.18 的 `kref_put` 是裸 `atomic_dec_and_test`，无饱和保护）＝**UAF** ✓
被释放的对象是 **`struct ion_handle`（ref0/client8/buffer0x10/node0x18/id0x30/kmap_cnt0x34 ⇒ 0x38=56 → kmalloc-64）**，`ion_buffer`(192) 反而因为 `ION_HEAP_FLAG_DEFER_FREE` 可能只是挂到 freelist 而**不立刻 kfree**（待本机确认）。

**为什么这反而更好**：`ion_handle_destroy(fake)` 的整条操作数都能指向**我们的用户态页**——
`handle->client`(fake+8)、`handle->buffer`(fake+0x10) 都由喷射内容决定，而喷射内容我们从头一个字节就可控 ⇒
1. `mutex_lock(&buffer->lock)`、`idr_remove(&client->idr, id)`（空 idr ⇒ 返回 NULL，安全）
2. **`rb_erase(&handle->node, &client->handles)`** ⇒ `__rb_change_child` 把 **NULL（或我们指定的 child 指针）写入 `parent+8/+16`** ⇒ **任意地址写零 / 写指针**，且**附带写只落在被喷对象自身**（children=NULL 时 `s==NULL` 走不到 `rb_set_parent_color`）＝**干净的一发写原语**
   ⇒ `parent = selinux_enforcing-8` ⇒ **写零 ⇒ SELinux permissive**（静态地址，无需泄露）
3. `ion_buffer_put(handle->buffer)` 指向**用户态假 buffer** ⇒ `kref_put` 读 `*(user+0)=1` ⇒ `_ion_buffer_destroy(user_fake)` ⇒
   `heap`＝用户态假 heap（+0x38 正好是 `cred->user` 槽）→ `ops`＝我们给的假 ops 表 → **`ops->free(heap, buffer)` = `commit_creds(U_heap)`**
   ⇒ `U_heap` 同时就是我们精心构造的**用户态假 `struct cred`**（uid/gid/cap 全 0/全满、三个 key_serial=0、`user` 字段兼职当 ops 指针 ⇒ `get_uid` 只是对我们用户内存 atomic_inc，无害）
   ⇒ **一次劫持同时拿到"写零关 enforcing"和"以 x0=用户假 cred 调 commit_creds"**，且**不需要内核代码执行/ROP/pivot**（3.18 arm64 无 UA/PAN 硬化，内核可直接解引用用户指针）
**触发器**：`close(SHARE 出来的 fd)` → `ion_dma_buf_release` → `ion_buffer_put(buffer)`（源码已核）——由我们择时，喷射压力可以从容。

## 19. ★★UAF 已被证实命中（第一次跑就命中），并定位到 panic 的确切成因

崩溃点由源码逐行锁定（`ion_handle_destroy` 的次序）：
```

kfree(handle)           → 释放我们那个 setxattr 的 kmalloc-64 对象（自身，安全）
```
⇒ **结论：假 handle 确实被内核当作真对象走完了整条 destroy 路径**（否则不可能到 `BUG_ON`）＝竞态命中＋喷射接管都成立，一次就中。
⇒ **写原语在 `BUG_ON` 之前执行**：那次如果 `parent` 指向 `selinux_enforcing-16`，enforcing 已被写 0，才轮到 panic。

### 下一版必须改的 4 点（都在源码里，不是猜）
1. 假 buffer `handle_count@+0xa8` 设 **≥2**（减完仍 ≥1 ⇒ 跳过 `BUG_ON` 与 `get_task_comm`）
2. 假 buffer `lock@+0x50` 保持全零用户页（mutex 快路径 cmpxchg 0→current 成功）✓ 已满足
3. `rb_erase` 的 `parent = selinux_enforcing(0xffffffc00189be74) - 16`、`color=RED(|1)`、两子指针 NULL
   ⇒ `__rb_change_child` 走 `else` 分支把 **0 写进 parent->rb_right = selinux_enforcing** ⇒ permissive，且无附带写
4. `ion_buffer_put` 阶段先保持 `ref=0`（不进 destroy）⇒ 本发只求 **permissive 存活**；
   下一发再把 `ref=1` ＋ 完整假 buffer/heap/ops ⇒ `heap->ops->free(heap, buffer)` = `commit_creds(假cred)` 拿 uid0＋cap

## 21. 为什么"7 次 4 字节写"这条链是自校正的（关键设计）
落地一次 = 一次 `atomic_sub(size, &heap+OFF)` = **4 字节写**（value = 旧值 − size）。要拿到 root 需要：
1. `selinux_enforcing(0xffffffc00189be74) ← 0`（判据 `getenforce`＝Permissive）
2. `modprobe_path(0xffffffc001635a30)` 逐 4 字节拼出 `/data/local/tmp/rootsh`
   ⇒ **permissive 之后 `/proc/sys/kernel/modprobe` 变成可读**（`cat` 它 = 直接看到当前真实内容）
   ⇒ 所以每一发写完都**回读校验**：算 `size = 观测到的旧字 − 想要的新字`，打偏了就补偿重打 ⇒ 对"同一发里多余 put 落两次"免疫 ✓✓✓
3. `execve` 一个坏 Magic 的文件 ⇒ `call_modprobe` 以 root 执行 modprobe_path ⇒ `rootsh` 落地
   （注意 kmod 会带 argv `["-c","/dev/null",…]` ⇒ rootsh 必须无视参数）
失败就重启：`enforcing=1` 与 `modprobe_path="/sbin/modprobe"` 都是**重启即回到已知初值**的 RAM 状态 ⇒ 整条链可重复、可回退，正符合"临时"。

## 23. 堆枚举 + 触发机制的真正理解（本轮实测）
- heap_id_mask：bit **0..8 = ENODEV**，bit **9 可分配**（system 类，`ion_system_heap_create` 置 flags=1 ⇒ DEFER_FREE，首次 destroy 不 kfree），bit **10 存在**（跑到它时设备掉线 ⇒ 该堆可能不 defer 且我们的模子在某处被用了）
- `ion_cma_heap_create / ion_system_contig_heap_create / ion_secure_cma_heap_create / ion_heap_create` **不写 flags=1** ⇒ 这些堆首次 destroy 就 `ion_buffer_destroy`→真 kfree ✓
- ★机制纠正（比 §17 更准）：多余 put 打的不是"空槽"而是**下一次 ALLOC 刚复用同一 kmalloc-64 槽的活 handle**
  ⇒ 活 handle 被提前 destroy ⇒ 它的 `ion_buffer_put` 把 buffer 提前释放 ⇒ **我们仍握着 ION_SHARE 的 fd**
  ⇒ 于是 `close(fd)` = 由我们择时的第二次 `ion_buffer_put` ⇒ 在"释放"与"引爆"之间可以尽情喷射 kmalloc-192，
  **不需要赢纳秒级竞态，只需按次记账 fd**（每轮用**独立的 /dev/ion fd**＝独立 client，减少互相踩踏）
- `PRINTK` 我先前填成 `0x220aa0`，实为 `warn_slowpath_fmt`（会把 x2 当 fmt 解引用＝自找崩）；真 `printk` = **0xffffffc000d8fad8**
- `msm_dma_buf_freed(buffer)` 实测只在一张全局表里按地址查找，**不解引用 buffer** ⇒ 假 buffer 进 destroy 的第一道安全 ✓
- 待办：`ion_root.c` 改成多 client 版本（每轮 open 一个新 /dev/ion、ALLOC+SHARE 后留 fd；喷射 192B；再逐个 close）
  阶段顺序：probe(只 printk 标记，parent 指自己用户页) → enforce(写 selinux_enforcing=0) → root(ops[0x08]=commit_creds)

## 24. 实测出的调用约定（推翻按 C 原型的推断）＋ 分阶段定案
`ion_buffer_destroy` 反汇编（0xffffffc0009e7940 段）证明：
- `ops[+0x20]`、`ops[+0x30]` 的调用是 **x0 = heap**（`ldr x0,[x19,#0x28]` 之后没再改）
- `ops[+0x08]` 的调用是 **x0 = buffer**（`mov x0, x19` 之后 `blr x1`）
- 尾部：`x0=[x19,#0x90]` 若为 0 就跳过 `vfree`；然后 **`kfree(buffer)`**
⇒ 因此 **`commit_creds` 必须挂在 `ops[+0x20]`（x0=heap）**，`heap` 那页同时就是假 cred；
   `ops[+0x08]` 放一个"单参数无害"函数（printk；x0=buffer 页首字节是 ref=0x01，只打几个字节就撞 NUL）
⇒ 之后那次 `kfree(buffer=我们自己的用户页)`：会把**属于我们自己的物理页**误放回 buddy（温和、可容忍），
   而此时 `close()` 返回用户态的我们**已经是 uid 0** ⇒ 立刻 exec rootsh/frida ⇒ 抢在该页被再次使用前完成

## 25. 两阶段定案（阶段 A 完全无害，先做）
**A. 关 SELinux（幂等、零风险）** —— 走 handle 路径的 `rb_erase`：
   假 handle(+0x18) = `(selinux_enforcing-16)|1`，两子指针 NULL ⇒ `__rb_change_child` 走 else 分支
   ⇒ **把 0 写进 `selinux_enforcing(0xffffffc00189be74)`**；`s=NULL` 故无附带写 ✓ 可重复（幂等）✓
   同时 `handle->buffer` 指用户页、`handle_count=5`（只减不触 0 ⇒ 不进 atomic_sub、不触发 BUG_ON）
   判据：`getenforce` → Permissive（写错就不变，天然正/负控）
**B. 拿 uid 0** —— `heap` 页＝假 cred，`ops[+0x20]=commit_creds`，`ops[+0x30]=printk`，`ops[+0x08]=printk`：
   cred 字段按 `commit_creds` 实测偏移摆：`usage@0`(大)、`uid..fsgid@8..0x27`=0、`secure@0x28`=0、

## 26. 阶段 A（rb_erase 写 0）实测又崩 ⇒ 换写原语，并给出理由
`stageA`（3 racer、`handle_count=5`、parent=selinux_enforcing-8）round 0 就掉线。
逐条核对后确认**写点本身是对的**：`and x4,x5,#~3` → `str x3,[x4,#8]`，`x3=rb_right=0` ⇒ 写 0 到 `enforcing` ✓；
但 `rb_erase` 在写完后还要走 `0x49a528` 起的尾巴（`ldr x3,[x2,#8]` 之后**把 parent+8 当节点继续解引用**），
只在 `x3==0` 时才 `b.eq 0x49a60c` 绕开——这条控制流我没能全程跟死，**不能拿它当"稳定"依据**。
⇒ 定案：**弃用 rb_erase 作写原语**，改用 `ion_buffer_remove_from_handle` 里那条
   **`ldxr w2,[heap+0xec] ; sub w2,w2,w1(=buffer->size) ; stlxr`** 的**纯直线 RMW**（无指针追逐、无分支）：
   - 目标值可精算：`old` 已知 ⇒ `size = old - new (mod 2^32)`
   - `selinux_enforcing`：getenforce 观测 old=1 ⇒ size=1 ⇒ 写 0 ✓
   - `modprobe_path`（.data，初值逐字节已知）：6 发 4 字节写拼出 `/data/local/tmp/rootsh` ✓
   - **闭环校验**：permissive 之后 `/proc/sys/kernel/modprobe` 可直接 `cat` ⇒ 多落地导致的过减可**回读后补偿重打** ✓✓
   代价：`handle_count` 归零那一发才写，重复落同一枚模板会 `BUG_ON` ⇒ 每轮只放 1 枚模板＋落地即停（canary 在进程内自检）

## 28. 竞态编排的三种形态（全部实测，5 次重启换来的结论）
| 编排 | 结果 | 解释 |
|---|---|---|
| **v3**：每轮**新建 client**（id 恒为 1）＋保留 share fd＋≤3 racer | 干净跑完，canary 未动 | 多余 put 落在**尚未被复用的已释放槽**上：`atomic_dec_and_test` 见 0→−1 不回调 ⇒ **静默无害**（这就是"没命中"的真相，不是窗口没开） |
| **v4a**：**同 client**，FREE 风暴后再 ALLOC H2（复用受害者），且**提前 close H1 的 share fd** | **卡死**（设备活着，进程 D 态） | 提前 close ⇒ buffer 进 DEFER_FREE 链表；多余 put 去拿"正被 delayed work 回收的对象"的 mutex ⇒ 自锁 |
| **v4b**：同 client＋fd 全留住 | round 0 **崩** | 提前销毁真的发生了（真内存效应），但我还没把被复用的那枚对象换成**可控内容** |
⇒ 结论：**要"可控落地"必须同时满足**（1）同一 client 内风暴后继续分配（制造复用受害者）（2）share fd 一律留住（3）喷射对象尺寸要匹配**被释放的那枚**＝kmalloc-**64**（handle），不是 192。
`stageB` 也证明了计数通道：`id=0x7fffffff` + 全零 client ⇒ 每次落地必过 `idr_remove` 的 **WARN** ⇒ **dmesg 可数**；`handle_count=0x7fffffff` ⇒ 永不进写分支 ⇒ 不触发 BUG_ON ⇒ 安全的"落地计数器"。

### 33.1 驱动常量的真值（不信 CAF 头，信本机二进制＋真机枚举）
- BC_* 的 type 字符是 **'c' 不是 'b'**：从 binder_thread_write（0xffffffc0009f669c）的 switch
  比较常量直接解出：0x630b/0x630c/0x630d（REGISTER/ENTER/EXIT_LOOPER）、0x40046302、
  0x40086303(BC_FREE_BUFFER)、0x40046304..07、0x4008630a、0x40106308/09、0x40086310。
- BC_TRANSACTION 真值用**枚举 size 字段**在真机上问出来：只有 0x40406300（type 'c', nr 0,
  size 64）被接受（rc=0, write_consumed=68），其余 8..128 全部 -EINVAL。

### 33.3 binder_poll 在本机的真实分支（反汇编 ffffffc0009f5404 得到，CAF 源码只作参照）

### 33.4 唯一可注册状态 = 未回文的同步事务（本轮打通的关键）
- 需要同时满足：todo 空 && transaction_stack 非空(to_proc 已设) && return_error==BR_OK
  && NEED_RETURN 已清。
- 但 binder_transaction 在投递时给**发送方** todo 也挂一条 BINDER_WORK_TRANSACTION_COMPLETE
  （源码 binder.c:1703 对 sync/async 都做）⇒ 刚发完必不满足。
- 解法（tools/broot.c arm_pending_tx）：
  1) 发同步事务到 handle 0（service_manager，全局 context_mgr_node，shell 可达 ✓）
  2) 立刻读一次：**要解析整段命令流**，不能只看第一个 dword——新线程首次 read 会先吐
     BR_NOOP(0x720c) 清 NEED_RETURN，然后在同一次调用里继续吃 todo；
     只要这一批含 BR_TRANSACTION_COMPLETE(0x7206) 且**不含 BR_REPLY(0x80407203)** 就立刻收手
     ⇒ 此刻 todo 空、stack 还在 ✓✓（读到 8 字节 = NOOP+COMPLETE 就是理想态；
     读到 76 字节 = 连回复一起吃掉了 ⇒ stack 被清，本轮作废）
  3) 马上 epoll_ctl(ADD) → 注册到 thread+0x48
  4) ioctl(BINDER_THREAD_EXIT) → binder_free_thread（ioctl 内有 0x6208 比较 + bl 0x9f1218 ✓）
     → binder_release_work(todo) → **kfree 无条件**；transaction_stack 的 t->from 被置 NULL，
     故随后 service_manager 的回复走 BR_DEAD_REPLY 分支，不会再解引用已释放线程 ✓ 安全
  5) writev(pipefd, iov[25], 25) → rw_copy_check_uvector 对 nr_segs>8 做 kmalloc(400) →

  6) 子进程（同在 CPU0）EPOLL_CTL_DEL → ep_unregister_pollwait → ep_remove_wait_queue →

- 竞态胜率：本轮 8 次里 3 次拿到理想态（complete=1 reply=0）并全部泄漏成功 ⇒ ≈40-50%/轮，

### 37.2 ★算式：racer 数 T ⇒ 多余 put = T−1 枚
句柄 ref 初值 1；每个 racer `get_by_id`(+1) 后做两次 put ⇒ 第 (T+1) 次 put 把 ref 打到 0
⇒ 真句柄 destroy＋`kfree`；其后还剩 **2T−(T+1) = T−1** 枚 put 打在已释放的槽上。
* T=4 ⇒ 3 枚：第 1 枚走完我们整条链（含尾部 `kfree`），槽位回到 freelist；
  **第 2 枚的 `atomic_dec` 直接改写了 freelist 指针（SLUB 把 next 存在对象偏移 0）** ⇒ 当场炸 kmalloc ✓ 与 37.1 吻合
* **T=2 ⇒ 恰好 1 枚多余 put**（唯一"自我限量"的形状）；T=1 ⇒ 0 枚（无 UAF）
⇒ `iroot` 的 racer 数改成 CLI 参数（默认 2）。这比"喷得更凶"重要得多。

### 37.3 ★★喷射对象的**寿命**才是能不能活的关键（结构性结论，别再走回头路）
落地链的尾部必然执行 `kfree(handle)`＝**替当前槽主把对象释放了**。所以喷射对象只有两种下场：
(a) 属主之后还会自己 free ⇒ **double free** ⇒ freelist 同一槽出现两次 ⇒ 两次分配拿到同一地址 ⇒ 迟早炸；
(b) 属主**永不** free ⇒ 我们那次 `kfree` 就是唯一一次合法释放 ⇒ 干净。
实测与推导都指向：`setxattr` 的 64B 对象是 ext4 `new_entry` 这类**同一 syscall 内就 kfree 的暂存缓冲**
⇒ 属 (a) ⇒ "命中即埋雷"，这就是 4 racer 之外仍需担心存活性的原因。
能在 shell 域造出 **(i) 偏移 0 起全是我们给的原始字节 ＋ (ii) 长时间不释放** 的对象，目前只找到一类：
**阻塞在内核里的 `writev/recvmsg` 的 iovec 数组**（`import_iovec` 对 nr_segs>8 才 kmalloc，数组内容
＝我们给的 base/len 原始 8 字节对，且线程阻塞期间内核一直持有它；我们只要不唤醒它就永不释放 ✓）。
**尺寸是硬约束**：每段 16 B ⇒ 9..12 段 = 144..192 B ⇒ 只能落 **kmalloc-192**；4 段以下走内核栈（不 kmalloc）。
⇒ 而 `kmalloc-192` 正好是 **`struct ion_buffer`** 的尺寸档 ⇒
**战略结论：把 UAF 目标从"64B 的 ion_handle"换成"192B 的 ion_buffer"，触发器用我们自己择时的 `close(share_fd)`**
（§23 已证 `ion_dma_buf_release`→`ion_buffer_put` 由我们控制），喷射不再需要抢纳秒窗口，

- 喷射对象＝**阻塞在内核里的 writev/recvmsg 的 iovec 数组**：属主是我们的阻塞线程，
  内核全程**不会 kfree 它**（只有 syscall 返回时才 free，而我们不唤醒）⇒ 不存在 §37.3 的 double free；
- 落地率本机实测 ≈40-50%/轮（§33.4），失败轮不伤机；
- 拿到任意读写后**可以先读后写**：读 `selinux_enforcing` 应为 1、读 `current->cred` 应为 shell 的 cred
  ⇒ **生效前就有正控**，比 ion 那种"打了才知道"的一发自减稳得多 ✓✓✓
### 38.3 生效序列（broot2 要做的，全内存态、重启即复原）
1. stage1 竞态（已通）→ 泄漏窗 → 定出 `slot VA`、`E`、`current_ptr`（本机偏移从泄漏里找，正控＝
   `current_ptr+0x4a8` 读出来应等于我们自己的 cred 指针、`+0x470` 应等于本进程 pid ✓ 两处可自证）
2. `list_add` 覆写第 5 段 `iov_base` → 灌 `second_write_chunk` → 把 addr_limit 抬成内核堆地址
3. **读校验**：`kernel_read(selinux_enforcing)==1`、`kernel_read(init_cred+0x00)==4`
4. 写：`selinux_enforcing = 0`（4 字节，地址已 §30+§37.5 两路确认）→ `getenforce` 必须变 Permissive
5. 写：`current->cred = current->real_cred = init_cred(0xffffffc001636d80)` ⇒ uid0＋全 cap＋init 的 SID
   ⇒ 再立刻把 addr_limit 还原成 0x7ffffffff000（收尾，避免其它 syscall 的校验失效）
6. `fork+exec /data/local/tmp/rootsh`（常驻，adb forward tcp:12345）→ frida-server 落地
### 38.4 ion 侧本轮补的三条硬事实（留作备胎，别再重推）
- `ion_dma_buf_release(dmabuf)` 只有 6 条指令：`ion_buffer_put([dmabuf+0x78])` ⇒ `struct dma_buf.priv@0x78`，
  触发器完全由我们 `close()` 决定 ✓
- `ion_handle_put(handle)`：`down_write(&client->lock)`（**client+0x50**）→ `atomic_dec` → 可能 destroy → `up_write`
  ⇒ 双 put 会**顺带把真实 client 的 rwsem 计数打偏** ⇒ §28 v4a 那种"进程 D 态卡死"就是它，不是 slab ✓
- `ion_share_dma_buf` 里确实有 `ldxr/add/stlxr`＝**一次** `kref_get(&buffer->ref)`（+0）；
  ⇒ "让 buffer 在 dmabuf 还指着它时提前释放"仍需**额外的 buffer put**，只能由 64B 句柄槽的假对象给出
  ⇒ 与 §37.3 的死结同一个：192B 档能安全喷射，但 192B 档的提前释放需要 64B 档的假对象 ✗

## 57. binder 阶段二的关键结构事实：第一次 DEL 会把 pwq **释放**，所以 chunk 是写进"刚被 kfree 的 pwq 槽"
`ep_unregister_pollwait()`（fs/eventpoll.c, 3.18）在 `list_del/init` 之后 `kmem_cache_free(pwq_cache, pwq)`
⇒ §56 观察到的"chunk 写进 entry"实际是写进**已释放的 pwq 对象**（它自己就是 entry 的宿主）。
含义（这一条决定了下一步的形态）：
- 我们手里其实是"**在 slab 生命周期之后写 128 字节**"的原语，落点是内核挑的那个槽；
- 于是"第二次链表操作"不能靠另一个 epoll（每个 epoll 有自己的 pwq，被污染的那枚不会再被引用）；
  可行形态只有两种：
  (a) **让别的对象复用这枚 pwq 槽**，然后内核在"用它"的过程中把我们的字节当指针解引用
      ⇒ pwq_cache 只有 epoll 自己分配 ⇒ 需要"新建一个 epoll 监听一个 fd"来回收同一枚槽，
        再让该 fd 的 wait 头被删除/唤醒时读我们埋下的 next/prev ⇒ 这条**结构上可行**，
        且回收是确定性的（同 CPU 同 cache，先 free 后 alloc）——正是 ion 那节我误判为"抢不到"的
        同一形状，这里 free 与 alloc 之间是我们自己控制的间隔（不是 µs 级同线程背靠背）✓
  (b) 或者放弃"第二次链表操作"，改用 **`ep_poll_callback` 的 wake**：head 已被我们改写
      （[5].base/len＝head 自链）⇒ 若能让 binder 再 wake 一次该 head，就会顺着我们的指针走一遍
      `__wake_up` 的表遍历 ⇒ §42 已实测"没有 wake"，这条要先证伪/证实，成本高。
⇒ 下一步按 (a) 做：broot8 = 现有 broot7 流程之后，**在同 CPU 上创建一个新 epoll 并 ADD 若干 fd**
  （回收那枚 pwq 槽），然后对回收者做一次 DEL ⇒ 若 DEL 读到的 next/prev 仍是我们埋的值，
  就会做 *(next+0x10)=prev 与 *(prev+8)=next 两发**地址可选、值为指针**的写；
  selftest 把两个落点都设成我们自己的页（canary-0x10 / sink-0x8）⇒ 零风险可观测。

## §67 【重要更正・§66 作废】binder UAF 的"自指 list_del"恰好就是我们要的写原语；broot8 的"无页改变"是管子路径的 access_ok 拦的，不是形状不可达

读 `pocs/cve2019-2215-3.18-master/poc98.c`（Jann Horn / Maddie Stone, PJ #1942）全文后，把机制重新对齐本机常数，纠正 §66。

### 1. §66 的错处
§66 说：`remove_wait_queue` 的 `__list_del(head, head)` 只写 `slot+0x58` 和 `slot+0x60`，`slot+0x50` 保留 `add_wait_queue` 留下的 pwq 地址，所以迭代器永远停在被污染的那段、永远走不到重定向后的下一段。
两处错：
* 字段选错。`wait_queue_head_t = { spinlock_t lock; struct list_head head; }`，本机 `wait@0x48` ⇒ lock@0x48、`head.next@0x50`、`head.prev@0x58`。`pwq->wait.task_list` 的 next/prev 都等于 **`&head->task_list` = `slot+0x50`**（不是 `slot+0x48`）。
* 于是 `__list_del(P,N)`（P=N=`slot+0x50`）先 `*(N+8)=P` ⇒ **`slot+0x58 = slot+0x50`**，再 `*(P+0)=N` ⇒ **`slot+0x50 = slot+0x50`**。
  ⇒ `iov[5]` 两半同时变成 `slot+0x50`：**base 是内核地址、len 是一个巨大内核指针**。这正是污染对的形状。
* "迭代器不推进"不成立：`memcpy_to_msg` 的每段拷贝量是 `min(现在读到的 iov_len, 这一段还剩多少)`，而 **整条 msg 的总预算在 import 时按原始 Σlen 定死**。段 [5] 的原始 len 我自己给（例如 0x50），所以它照 0x50 字节拷完就推进到 [6]，而 [6] 的 base/len 刚从内核里被段 [5] 的拷贝改写过 ⇒ **[6] 起可以指向任意内核地址**。

### 2. 真正的写通道（比 PoC 还少一步：不需要 addr_limit）
AF_UNIX SOCK_STREAM 的 `recvmsg(MSG_WAITALL)`：每次 `write()` = 一个 skb = 一次 `skb_copy_datagram_iovec`，逐段现读 `iov_base/iov_len`，而且它走 `__copy_to_user`（raw，**不做 access_ok**）⇒ 目的地是内核地址也照写。
链：`EPOLL_CTL_ADD(binder_fd)`（`binder_poll`→`binder_get_thread` 建 thread，并把 `pwq->whead` 指向 `&thread->wait`）
→ `ioctl(fd, BINDER_THREAD_EXIT)`（todo 空、return_error=BR_OK ⇒ `binder_free_thread`→`kfree`，slot 进本 CPU 的 kmalloc-512 free list）
→ 父进程 `recvmsg`（18 项 iovec 数组，18*16=288 ⇒ 同 kmalloc-512 ⇒ 抢回那枚 slot）
→ 子进程 `EPOLL_CTL_DEL` ⇒ `ep_remove`→`remove_wait_queue`⇒ 上面那两笔自指写 ⇒ `iov[5]` 中毒
→ chunk1（installer）写进 `slot+0x50`：把 `iov[6].iov_base` 装成 `selinux_enforcing`、`iov[6].iov_len` 装成 4
→ chunk2（payload）的头 4 字节 = 0 ⇒ **`selinux_enforcing = 0`**，Permissive。
broot8 用 pipe+`readv` 读到"没有一页被改"现在有了确定解释：**`pipe_read` 走带 access_ok 的 `copy_to_user`，内核目的地被静默拒收**，不是形状不可达。broot6（socketpair+recvmsg）当时的"38/40 命中"是同一件事的真信号，被我自己的 filler 溢出误判掉了。

### 3. 顺带：poc98.c 的 `clobber_addr_limit()` 是半成品

## §69 写链的真实机制（实验＋源码双证），以及"装第二枚段"为什么不可能

实验事实（broot11/broot12/broot13，本机，shell uid 2000）：
1. armed 态成立；`BINDER_THREAD_EXIT` 无条件 `kfree(thread)`；**25 项 iovec 数组（400B，kmalloc-512）确实抢到了那枚 slot**：broot12 的 socket 版 12 轮里 9 轮 seg5 的 user 缓冲没被写＝数据去了内核；broot11 dgram 版 8 轮里 7 轮同理。
2. `EPOLL_CTL_DEL` 的 `remove_wait_queue` 自指 `__list_del` 把 **`slot+0x50` 这个值**同时写进 `slot+0x50` 和 `slot+0x58` ⇒ `iov[5] = {base=slot+0x50, len=同一个内核指针}`。
3. **`iov_iter` 不会重读 `iov_len`**：broot12 里 chunk1 已把 `slot+0x58` 愈合为 0x50，但后续数据仍全部留在这段里（4 个 sink 全 0、marker 不动）。⇒ 一个被污染的段会吞掉整次调用的数据，**"先愈合再交给下一段"在同一次拷贝里做不到**。
4. 拷贝的 range-check 不对称（这是 §67/§68 判断的真正修正）：`memcpy_from_msg`/`memcpy_toiovec`→`__copy_*_user` 不查 ⇒ **读方向（内核→用户）确实成立**（broot 的 leak ✓），`memcpy_to_msg`→`copy_to_user` 查 ⇒ **写方向对被污染成内核地址的 `iov_base` 会 EFAULT 并中止整次拷贝**（broot13 那次 `recvmsg=-1 EFAULT` 就是直接证据）。⇒ **socket 收包这条路给不了内核写。**
5. 结论：目前唯一稳的内核能力 = **任意内核读**（broot 型：armed+free+抢slot+DEL，然后 pipe writev 停在数组里，中毒段把 `slot+0x50` 起的内核内容送进管子）；**内核写需要另一种载体**：拷贝进 `iov_base` 且不查 range 的 recvmsg 路径（本内核没有），或者换漏洞面。
6. 工程细节（踩过两次）：**writev 必须"停在数组里"**——管子容量要设成 1 页、且第一段是 dummy，child 先排干一页、再做 DEL、再排干中毒段并转写进 leakPipe；如果 Σ 长度 ≤ 管子容量，writev 秒回、数组随即 kfree，150 ms 后的 DEL 就只会中毒陌生人（broot13 首版 0/12 就是这个）。
7. 顺带：`access_ok` 与 PXN 是两条独立的位；本机 3.18 无 PAN ⇒ 内核能直接读写用户页（读已实测成立），但用户页带 PXN ⇒ 内核不能执行用户代码，所以 `__wake_up_common` 的 `w->func` 劫持只能跳内核符号。
8. 下一步选项（二选一，按性价比）：
   A. 换载体做内核写：`kgsl` BadPage 型 GPU 全局窗口跨接（`kgsl.c:3544` MAP_FIXED + `kgsl_iommu.c:1871-1884` 只测端点，`kgsl_iommu_map_globals()` 不入 rbtree），需要发 CP 命令，工程量一档，但没有 range-check 问题；
   B. 继续 binder：**用中毒段把伪造的 wait 链表写进 `slot+0x48..0x58`**（`head.next/prev` 指向我们自己那枚数组里的伪造 `wait_queue_t`），再让内核自己 `wake_up(&thread->wait)`——本机唯一稳定给已释放 thread 发 wake 的入口是 `binder_send_failed_reply()` 里 `target_thread = t->from`，而 `t->from` 要活过 `binder_free_thread()` 的清扫，就得让该事务不在被释放线程的 `transaction_stack` 链上（＝对端先成功 reply 把链摘掉＝需要两个自有进程 + servicemanager 交换句柄；`service add` 在本机 `service` 工具里没有子命令，得自己发原始 BC_TRANSACTION 试 SELinux 是否放行 shell 的 `service_manager add`）。

## §71 binder 外部写：三条独立的结构性堵点，路线关闭（本轮实验定论）

想从"我已经能把自选字节写进那枚已释放 binder_thread 槽"（broot12 实测成立）跨到"往槽外写"，本轮把最后一条看起来可行的路（`binder_release_work` 的 `__list_del` 双写）做完，结论是**不通**，三条独立原因：

1. **释放顺序天生反了**：`binder_free_thread()` 是 `binder_release_work(&thread->todo)` **然后** `kfree(thread)`（binder.c:2594-2595）。要让 release_work 消费我伪造的链表头，头必须在我*还没*拿到槽之前就是假的；而我唯一能写槽的时机是槽已被释放之后 ⇒ 永远错过消费者。实测：broot14 两种顺序（free 前 / free 后 recvmsg）都没有产生任何外部写，机器也不崩（=没有陌生人被写）。
2. **收包路径不重读 `iov_len` + 目的地过 `access_ok`**（§69）：中毒段吞掉整次数据，交不出第二段的"重定向"；而就算交出去，`memcpy_to_msg`→`copy_to_user` 会拒内核地址（broot13 实测 errno=14）。
3. **能存进去的值只有"槽自己所在的指针"**：`__list_del` 两笔写的值分别是 myNext/myPrev，二者都必须是可写地址；即便取"自我回指"那组（`slot+0x50`）能得到一个 ≥0xffffffc0 的数值（PAGE_OFFSET 在本内核＝0xffffffc000000000，见 §72），第二笔写会落在 `slot+0x10`（rb_node 区）＝自己槽内、可接受 ⇒ 理论上一笔存"栈/页指针"是成立的——但前提是有个消费者去读我伪造的头，即被第 1 条堵死。

顺带钉掉另一个候选：`add_wait_queue`（第二次 `EPOLL_CTL_ADD`）确实会按 `head->prev` 间接写 ⇒ 但 `head` 只能是新 thread/proc 的真头，不会是我中毒的槽 ⇒ 不可用。

⇒ **⇒ binder（CVE-2019-2215）在本机能拿到的只有：确定性内核读（broot 型）＋把自选字节写进那枚被释放的 binder_thread 槽。二者都到不了"改 `.data`/`cred`"。**
⇒ 与作者自证的边界一致：`pocs/cve2019-2215-3.18-master/README` 只说基于 Project Zero 的 *leak* PoC；其 `clobber_addr_limit()` 在 `main` 里是 `#if 0`、子进程分支里还有 `exit(0)` 之后的死代码 ⇒ 那半本来就没被作者验过（我早先记过这条判据，这次是自己没守住：见 [[feedback-port-poc-preconditions-not-just-constants]]）。

## §72 本轮新增的硬事实（可复用常数）
- `PAGE_OFFSET = 0xffffffffffffffff << (VA_BITS-1)`，且 memory.h 注释 "PAGE_OFFSET – the virtual address of the start of the kernel image" ⇒ 本内核线性映射从 `0xffffffc000000000` 起，**kmalloc/栈/struct page 的指针数值都 ≥ 内核镜像地址**（我整轮会话先前假设线性映射在 `0xffffff80…`、"比 `.data` 低"是**错的**）。Image header `text_offset = 0x80000` 与 `VA=0xffffffc000080000+off` 自洽 ✓。
- `.bss` 一直到 `__bss_stop = 0xffffffc001b3eff0`（`_end = 0x1b43000`）⇒ `selinux_enforcing`（`int selinux_enforcing;` 无初值＝在 .bss）在 `0xffffffc00189be74` 这个量级是**合理**的，"超出 Image 文件大小"不构成反证（我一度这样怀疑，已撤回）。
- `binder_thread` 偏移（源码逐字段算过，和 binder_poll 反汇编一致）：proc@0x00 rb_node@0x08 pid@0x20 looper@0x24 **transaction_stack@0x28 todo@0x30/0x38 return_error@0x40 return_error2@0x44 wait.lock@0x48 wait.head.next@0x50 prev@0x58 stats@0x60**。
- `struct binder_proc` 首字段是 `proc_node`(hlist_node)→threads→nodes→refs_by_desc→refs_by_node→pid→**vma**→vma_vm_mm→tsk→files→… ⇒ `todo` 不在 0x00（我先前记成 0x00 是错的）；`sizeof` 必 >512 ⇒ 不在 kmalloc-512。
- kgsl 侧实测（arm64/arm32 都跑通）：`open` ✓、`GPUMEM_ALLOC_ID` ✓、`DRAWCTXT_CREATE` ✓（shell 能开 GPU 上下文）、mmap 成功（**offset 必须 `id<<PAGE_SHIFT`**）、`GPU_COMMAND` 尚未跑通（IB 给了未定址缓冲）。SVM 区间 `[0x300000,0xBF000000]`/`[0x700000000,0x800000000]` 不含 `GLOBAL_MEM_BASE=0xF8000000` ⇒ BadPage 那种跨接在用户态拿不到（实测小 hint 全 ERANGE(34)＝被区间检查先拒）。
- servicemanager 侧实测（原始 `add_service`，两种 parcel 顺序都试，判据用框架自己的 `service check`）：**`service check xplay6q` → not found** ⇒ shell 不能注册服务（AOSP 6 的 C servicemanager 自己就要求 caller euid ∈ {system, root}，与 SELinux 无关）⇒ 依赖"我控制的另一端永不回包"的所有 binder 构造都不成立。

## §78 readv 路线的机制级结论（su98 不成立的原因）＋kgsl 提交面已打通但被 CP 包过滤挡住

**1. readv 写链在 3.18 结构上不可行（三条独立证据，全部当场实测）**

⇒ 已按源码逐字复制 `pm4_parity()`；核对：`cp7(CP_NOP,0)=0x70108000`（cnt=0→偶校验 1→bit15=1 ✓）、`cp7(CP_MEM_WRITE,4)=0x703D0004`（0x3d 折叠 nibble=0xe→bit23=0 ✓）。**判据：厂商头文件的位域/校验函数一律照抄，不许按"常识"重写**（同类事故：`memcpy_to_msg` 我按 4.x 记忆判断、系统调用号按 x86 记忆判断）。

- 写：`dst = args - overps[oix].offset`，`copy_from_user(dst, lpra[i].buf.pv, len = lpra[i].buf.len)`，
  守卫只有 `VERIFY(err, rlen >= mlen)` 且 `mlen = mend - mstart`。
"包含"分支把 `mstart/mend` 清零 ⇒ `mlen=0` ⇒ 守卫恒真 ⇒ 但**包含关系本身就是用 `(pv, pv+len)` 这对区间判定的**：
B⊆A ⇒ `offset = A.end - B.start` 且 `B.len ≤ offset ≤ A.len`；而 A.len 是**进 copylen 的那一项**。
⇒ 想写的长度 ≤ 已被分配覆盖的长度 ⇒ **越不出自己那页**。真机对照实验（`tools/arpc_scan.c`，四档）全部
`rc=-1 errno=1`＝驱动把越界的形状在 VERIFY 处拒掉（EPERM 是它自己把 copy_from_user 失败归一的返回值，非权限闸），
而 `offset=0` 的对照档能跑 ⇒ **这就是 85.1 的判决：不是"够不着 .data"，是"根本出不了页"**。

**85.2 但同一轮真机拿到两条硬能力，都还没被利用过：**
- **`IOCTL_KGSL_GPUOBJ_ALLOC`(0xC0300945) 对 shell 可用**：连开 24 枚 4 KiB 对象全 rc=0（id 1..24）。
  它内部 `kzalloc(sizeof(*entry))=272` ⇒ **kmalloc-512**，且 `copy_metadata()`（kgsl.c:3011-3024）
  `size = min(len, 64); copy_from_user(entry->metadata, to_user_ptr(metadata), size)`
  ⇒ **"把我选的 ≤64 字节写进一个 kmalloc-512 对象的固定偏移 +172"**＝天然的 Step B 落地点。
- 泄漏＋无 KASLR ⇒ 我能把一个 kmalloc-512 槽的**绝对内核 VA** 量出来，进而算出同页内所有邻居对象的 VA
  （同缓存对象按 `object_size` 等距排列）。

**85.3 于是缺口收窄成一件，而且只有一件：Step A ＝"把我选的 8 字节写进一枚**空闲**对象的头 8 字节"。**
拿到它之后不需要任何竞态：`kfree` 后的对象其 `next` 就在 `s->offset`（3.18 通用缓存无 ctor 无 red-zone ⇒ 偏移 0，
`msmcortex-perf_defconfig:25` 是 `# CONFIG_SLUB_DEBUG is not set`，真机上 `/sys/kernel/slab/*/{red_zone,sanity}` 文件不存在＝佐证），
把 `next` 改成 `modprobe_path-172` ⇒ 下一次 GPUOBJ_ALLOC 就返回那个 .data 地址 ⇒ `copy_metadata` 把
"/data/local/tmp/rootsh" 落进 modprobe_path ⇒ 执行坏 Magic 文件即由内核以 root 起我的 rootsh。
先写 `selinux_enforcing=0` 再写 modprobe_path 的顺序可以消掉"SELinux 不许 init/kernel 执行 shell_data_file"这个未知风险
（`execve` 坏 Magic 真机读数＝ENOEXEC，`/sbin/modprobe` 在本机不存在＝"missing"，都不构成反证，见 tools/modprobe_probe.c）。

**85.4 binder 那条 unlink 写的"值"不是我的（此前记的"能写 8 字节"要打折）**
`EPOLL_CTL_DEL → remove_wait_queue(wq=&slot+0x48, entry=&epi->wd.entry)` 里
`__list_del(entry->prev, entry->next)` 用的两个指针**存在 epi 对象内**（`epi_cache` 专用 slab，喷不到），
所以两个写的目的地都是内核自己那串链表指针（一个是槽自己）——这正是泄漏能成立、而"任意地址写"不成立的原因。
另一侧 `list_add(new, head)` 会读 `head->prev`（＝**我喷的值，可为任意地址**）并写 `next->next = new`：
**目的地我控、值＝那个 epi 的堆地址**。⇒ binder 能给的是"把一枚已知的内核堆指针写到我选的地址"，
不是"写我选的值"。这条区别要记死：**freelist 注入需要的恰恰是"值＝我选的 .data 地址"**，所以 binder 这条路对
Step A 无效（除非常规对象地址本身就是我要注入的东西，那没有意义）。

## §86 泄漏那把尺又被我自己的判据骗了一次（第三次），这次把判据钉死

`tools/broot.c` 原来的命中判据是 "出现非 marker 字节" ⇒ 零也算 ⇒ 假 LEAKED；我加了第一版严格判据
`qword >= 0xffffff8000000000`，本轮再改成 `>= 0xffff800000000000`，跑出 `kernel-VA qwords=156 → REAL LEAK`——
**仍然是假的**。逐条读数：
- 真机 20 轮里约 3 轮交付外来数据（`broot17`＝现源码重建，`rounds=16/20` 混合命中）。
- 那些"看着像内核 VA"的 qword 全是 `ffffc1xxxxxxxxxx` / `ffffc0xxxxxxxxxx` 形态，**不在本机 VA 空间里**
  （VA_BITS=39 ⇒ 线性映射 `0xffffffc000000000+phys`、vmalloc `< 0xffffff8000000000`、用户 `< 0x0000007fffffffff`），
  而且高频率出现的低 12 位是 `0x0ff / 0x8ff / 0x000` ⇒ 这是**数据**（形态像 IOVA/映射表条目，正合我刚用 markhold 开了 60 枚 GPUOBJ），
  不是指针。
- **一个 `v>>40 == 0xffffffc0` 的线性映射指针都没有**；`QMARK` 标记 **0 命中**。
⇒ 结论要按最保守的写：**"16 KB 内核堆读"目前只证明"能读到外来字节"，没证明"读到的是我知道地址的 slab 对象"**；
  槽的绝对 VA 这一轮也没能从流里取到（§42 那次靠"两枚相同的 0xffffffc06451ac50"取到，本轮流里没有这种形状）。
⇒ **判据换成三条必须同时成立才算命中**（下一步就先把它做进工装）：
  ① 流里出现我种在 kmalloc-512 对象 +172 的 `QMARK%03d` 字符串（＝证明窗口覆盖到 slab 邻居）；
  ② 出现 `v>>40==0xffffffc0` 且 `v-(0xffffffc000000000-0x80000000)` 落在 RAM 范围内的指针（＝证明是线性映射对象）；
  ③ 同一 qword 在流里出现的**偏移**与它数值的差，对 512 取模后一致（＝对象间距＝object_size 的自证）。
  三条不齐就报 "未命中"，不许写进账面当能力用。
- 顺带结掉一条：`markhold`/`arpc_scan` 都证明 **`IOCTL_KGSL_GPUOBJ_ALLOC` 连开 24~60 枚全 rc=0**，
  而 `/dev/sw_sync`、`/dev/gSync` 在本机**不存在**（按名单 stat 到），所以 kgsl 的 SYNCSOURCE 栅栏是唯一的栅栏来路。

## §87 泄漏窗口是**自描述**的：槽的绝对 VA 现在免费可得；并实测确认 SLUB 空闲指针在偏移 0

**87.1 流布局（逐字节对账，`/tmp/leak5.bin` len=86017）**
`tools/broot.c` 的 `writev` 段序决定了流的偏移：
`seg3 len=0x1000`（我的 filler 0x13）＋ `seg4 len=0x10001`（槽 +0x48＝等待队列 ticket 锁，一次 lock/unlock 后内核自己留下 0x10001，
于是"我的锁格"被当成**长度**用了 65537 字节——这本身就是命中证据）＝窗口起点 **0x11001 = 69633**，
再 `+0x4000`＝16384 ⇒ **4096+65537+16384 = 86017 与文件长度逐字节吻合**。
⚠ 我第一版分析把窗口当在 0x1000，且 `q(off)` 直接索引**文件**而不是"窗口+off"，两次都读出了假形状（0x1313…）。
教训：**流内偏移→绝对地址的换算必须带窗口基址，且对账文件总长度**。

**87.2 自描述指针＝免费的绝对读数**
`remove_wait_queue` 的 `__list_del` 把 `slot+0x50` 同时写进内核那份数组的 `iov[5].iov_base` 与 `iov[5].iov_len`；
拷贝的**源地址**就是 `iov[5].iov_base` 的值 ⇒ 于是**窗口的前 8 个字节等于窗口自己的源地址**。实测：
```
window[0] = 0xffffffc15ca80c50   window[8] = 0xffffffc15ca80c50   （两枚相同＝形状自证）
=> S = 0xffffffc15ca80c50, slot = S - 0x50 = 0xffffffc15ca80c00 （slot % 512 == 0 ✓）
=> phys = S - 0xffffffc000000000 + 0x80000000 = 0x1dca80c50 ≈ 7.45 GB（8 GB 机器，合理）
=> 槽所在页基址 = 0xffffffc15ca80000，页内 8 枚 kmalloc-512 对象，地址全部可算
```
⇒ **"我不知道内核堆在哪"这个前提已经不存在**；16 KB 窗口覆盖到 `0x...84c50`（我那片页＋后 3 页）。
**§86 的三条判据现在能自动判**：①两枚相同且 512-对齐＋0x50 的自描述指针；②落在 `0xffffffc0…` 线性映射且 phys 在 RAM 内；
③`slot % 512 == 0` 与"页基址 = slot & ~0xfff"的自洽。本轮三条全中 ⇒ **这才是真命中**（此前 156 枚"像 VA 的 qword"是 `ffffc1…` 形态，
在本机 39-bit VA 下既不是线性映射也不是 vmalloc ⇒ 是数据，判据当时太松）。

**87.3 SLUB 空闲指针位置实测确认：`s->offset == 0`**
按 512 对齐逐对象看**第一个字**：对象 `0xffffffc15ca80e00`（＝我的槽 +512）的首字＝ **`0xffffffc15ca80e00` 自己**
＝一枚 512-对齐的线性映射堆指针躺在一个对象的开头 ⇒ 与我"空闲对象头 8 字节＝next"的模型一致
（`# CONFIG_SLUB_DEBUG is not set`、无 red-zone、无 poison 的旁证到齐）。
⇒ **Step A 的目标物已经"看得见、算得出"：我邻格里确实存在空闲对象，且它的 next 字段就在 +0。**
⇒ 缺口仍然只有一件，而且现在有了具体形状：**把我选的 8 字节（＝`modprobe_path-172` 或 `selinux_enforcing-172`）
写进那枚 +0**。落地时不需要猜地址：`slotVA` 当场读到，邻格 = `slotVA ± k*512`。
（注意：注入之后下一次 GPUOBJ_ALLOC 返回该地址，`copy_metadata` 把我选的 ≤64 字节落在 `target` 处；
`selinux_enforcing` 只需 4 个零字节，`+4` 是 `sel_inode_cache` ⇒ **必须用 4 字节写**，或先关 SELinux 再动别的。）

`add_wait_queue` 的 `new->next = prev` 是**我选的值写进内核对象**——目标对象地址未知，但它是 epi/poll_table_page，

## §89 关键构造：把 binder 的"两笔链表写"串成**任意值写**——不需要 Step A（堆溢出）

3.18 `add_wait_queue(q, wait)` → `__list_add(&wait->task_list, q->prev? head, head->prev)`，一次调用**同时产生两笔写**：
| 写 | 目标 | 值 |
|---|---|---|
| W1 `new->next = prev` | `P + 0`（P＝被加入的 `wait_queue_t` 的内核地址） | **`prev = head->prev` ＝ 我在槽里种的 qword** ⇒ 值受我控 |
| W2 `prev->next = new` | **`Q1 + 0`**（`Q1`＝我种的同一个 qword） | `P`（内核堆指针） |

⇒ 于是一步同时得到：**"我选的值落在 P+0"** 且 **"P 落在 Q1+0"**。单独看都不是任意写，但**接上 SLUB 自己的取指针动作就够了**：
`kmalloc` 从 freelist 弹出一枚对象 X 后，把 `*(u64*)(X+0)` 当作新的 freelist 头（§88 实测：`s->offset==0`）。
所以：
1. 令 `Q1 = &<某枚 slab 页的 page->freelist>`（arm64 `CONFIG_SPARSEMEM_VMEMMAP` ⇒ `page = vmemmap_base + pfn*64`，
   而我**已经知道**我那页的物理地址＝§88 读到的 phys ⇒ `page->freelist` 的地址**可离线算出**，无需再读 .data）。
   一次 stale-head 的 `add_wait_queue` ⇒ `page->freelist = P`（合法堆指针，SLUB 照收）。
2. 下一次 kmalloc 弹出 `P` ⇒ `page->freelist = *(P+0) = W1 写进去的我选的值 Q2`。
3. 再下一次 kmalloc(272→kmalloc-512) **返回 Q2**。取 `Q2 = modprobe_path - 172`：
   `copy_metadata()`（kgsl.c:3011-3024）把 `metadata_len ≤ 64` 字节原样写进 `entry->metadata`＝**正好落在 modprobe_path**；
   随后 `kgsl_sharedmem_free` 之前的 `kzalloc` 已把 `[Q2, Q2+272)` 清零（＝副作用范围，见下面待核 ④）。
4. 执行坏 Magic 的文件 ⇒ 内核以 root 跑 `/data/local/tmp/rootsh`。先写 `selinux_enforcing=0` 再写 modprobe_path 更稳（4 字节）。

**待核清单（每一条都要引源码或真机读数，不许凭印象）**
① `__list_add` 里 `prev/next` 与我槽内 `+0x50/+0x58` 两个字段的**对应关系**（W1 读的到底是 `head->prev` 还是 `head->next`；
   3.18 `add_wait_queue` 是 `list_add_tail(&wait->task_list, &q->head)` ⇒ `prev = head->prev`＝**槽 +0x58**，
   而泄漏那两枚相同 qword 是 **+0x50/+0x58 都被写**——要逐行确认 W1 用的是 +0x58）。
② `new` 必须是**通用 kmalloc 桶**里的对象（`poll()` 的 `poll_table_page`＝`include/linux/poll.h poll_get_entry`，
   尺寸算式还没引到原文；若是 `epi_cache` 专用 slab，W1 的落点仍可用但"再被 kmalloc 弹出"那步不成立）。
③ **弹出顺序**：`c->freelist`（per-CPU，动态 `alloc_percpu`，地址未必可算）优先于 `page->freelist`；
   只有当 `c->freelist` 为空走 `activate_slab/set_partial_slub` 时才会用到 `page->freelist`。
   ⇒ 需要设计成"先把这枚 partial 页激活"或找到 `c->freelist` 的地址（可用 §88 的堆读＋`kmalloc_caches` 链去反推）。
④ 副作用范围：`kzalloc(272)` 会清 `[Q2, Q2+272)`。要么接受（先读 `art/kallsyms_real.txt` 看 modprobe_path 邻居是谁），
   要么改用**别的消费者**（`ION_IOC_CUSTOM`/`ashmem` 名字/小桶 `user.*` xattr）把清零范围压到 ≤64B，
   要么把目标选在**允许被清零的 .data 区间**。
⑤ 幂等/失败形态：W2 把 `P` 写进 `page->freelist`＝把一枚**活对象**放进空闲链（别名），第 2 步弹出它会破坏那枚 poll 对象；
   `poll()` 返回时 `kfree` 那页 ⇒ **同一槽被 free 两次**（我记忆里的 double-free 死结换了个位置）⇒
   需要让 `poll()` 永不返回（线程阻塞）或让那页由**永不释放**的持有者拿着。

**下一步**：把 ①②③④⑤ 逐条从源码钉死（①②③ 最关键，决定这套构造是否成立），
再做**只读**验证工装：先用一次"值＝指向我自己槽"的注入（不碰 .data），用 §88 的泄漏读回那枚槽，
若读到我选的值出现在本该是 next 的位置 ⇒ 链条成立；这一步不写任何内核 .data，可证伪、不炸机。

## §90 焊接引理（源码逐行核过，**推翻 §89 的可行性**）＋唯一能拆开它的形状

3.18 的链表插入（`include/linux/list.h:38-46`）：
```c
	next->prev = new;   new->next = next;   new->prev = prev;   prev->next = new;
```
而等待队列的加入（`include/linux/wait.h:114-117`）：`__add_wait_queue` = **`list_add(&new->task_list, &head->task_list)`**
⇒ `list_add` 展开为 `__list_add(new, head, head->next)` ⇒ `prev = head`（内核地址，不可选）、`next = head->next`＝**我槽 +0x50 那枚 qword**。
于是四笔写实际是：
| 写 | 目的 | 值 |
|---|---|---|
| `next->prev = new` | **`我的qword + 8`**（目的地可选 ✓） | `new`＝等待项地址（堆指针 ✗） |
| `new->next = next` | `new+0` | **我的同一枚 qword**（值可选 ✓） |
| `new->prev = prev` | `new+8` | `head`＝槽地址 |
| `prev->next = new` | 槽 +0x50 | `new` |

**焊接引理**：可选的"值"V 落在 `new+0`，可选的"目的地"D 是 `V+8` —— **D 与 V 是同一个变量**。
所以"先把某枚 freelist 头毒成 `new`，再让 `new+0` 的我选值成为下一次分配地址"这条链，
最终弹出的地址被钉死成 `freelist头地址 - 8`（＝`struct page` 数组 / percpu 区），**永远不是 .data**。
⇒ §89 的构造在 `list_add` 形状下不成立（我差点拿它去烧一发真机，这就是"两算式都要从同一棵树读"的用处）。
另核：`add_wait_queue_exclusive`/`__add_wait_queue_exclusive` 也只是多加 `WQ_FLAG_EXCLUSIVE`，仍走 `list_add` ✗。

**能拆开焊接的形状**：`list_add_tail(new, head)` ⇒ `__list_add(new, head->prev, head)` ⇒ `prev =` 槽 **+0x58**（可选）、`next =` 槽 **+0x50**（可选），
于是 `new+0 = +0x50 的值`、`new+8 = +0x58 的值`、`(+0x58 的值)+0 = new` —— **目的地与两个值来自不同字段，互不绑定** ✓✓✓
拿它串 freelist：`B = &<某 slab 页 page->freelist>` ⇒ `freelist = new`；弹出 new ⇒ `freelist = new+0 = A`（**A 任我选，比如 `modprobe_path-172`**）；
再弹出 ⇒ 该次 kmalloc 返回 A ⇒ `kzalloc` 清零 + `copy_metadata` 把字符串正好写在 modprobe_path ⇒ 坏 Magic 触发 ⇒ root。

⇒ **下一步的唯一问题变成一句可判定的话**：本机可达代码里，有没有一处
**`list_add_tail(&X, head)`，其 `head` 可以是我那枚被回收的 kmalloc-512 槽里的字段**（不只是等待队列）。
候选来路（都要引原文）：`binder_thread.todo`（槽 +0x30/+0x38，`binder_transaction` 的 `list_add_tail(&t->work.entry, target_list)`）
——但 `target_thread` 必须来自活的事务栈；以及 `epi->rdllist`/`ep->rdllist`（专用 slab ✗）、
`file->f_ep`/`inode->i_pipe` 之类。找到一处就成链，找不到就是死路（不许用 `list_add` 的变体凑）。

## §91 外部调研推翻了我"写方向不可能"的结论；我第一次跑 su98 移植把机器跑崩了一次（已恢复）

**91.1 我的 §10/§15/§53-63"binder 写方向不可能"是错的。**
`pocs/.../su98.c`（Alexander Pruss，LG V20 ＝ 同一枚 msm8996、3.18.71-perf）里
`clobber_data(payloadAddress, src, payloadLength)`（su98.c:187-294）**就是"任意值写到任意内核 VA"，且不需要执行任何代码**
（它的 root 段 su98.c:1377-1393 直接改 `cred->uid/securebits/cap_*` 与 `selinux_enforcing`）⇒ PXN 与"没有可用写"都不是障碍。
机制（我之前完全没想到的那一层）：
- 被污染那段的 `iov_len` 变成内核指针 ⇒ **段永远不会被喂饱** ⇒ `readv` 就停在那一段里；
- 于是我喂进管道的字节被**连续写进数组自己所在的槽**，把**迭代器还没走到的后面几枚描述符**改写成
  `{payloadAddress, payloadLength}` / `{&testDatum, 8}` ⇒ 游标走到时读的是**新描述符** ⇒ 载荷被投递到任意目的地址；
- `copy_to_user` 只在 `import_iovec` 时查过一次 `access_ok`（那时值还是用户指针），之后 `pipe_read→copy_page_to_iter→__copy_to_user_inatomic` **不再复查**。
⇒ 我先前否证用的是 `memcpy_toiovec`（错的路径）与"游标不重读数组"（对 `recvmsg` 成立，对 `pipe_read` 的**自改写**不成立）。
另一条我被自己误导的点：`su98` 的 `second_write_chunk` 用 `dummyBuffer` 吸收 `padding + 0x10001` 两坨（目的地＝**我的用户内存**），
所以那 64 KB 不会踩内核堆；被污染的 pair 段只吃到 `48 + payload + 8` ≈ 64 字节 ⇒ 正常应当是有界的。

**91.2 我这发的结果（全部读数留底）**
- 移植 `tools/clobber.c`（`IOVEC_ARRAY_SZ=18`，实测映射：lock＝e4 的 `iov_len`@+0x48，pair＝e5 的 base/len@+0x50/+0x58）。

  ⇒ 我的"selftest 目的地址是用户内存 ⇒ 零风险"的判断是错的：**污染段本身的目的地是内核**，写偏 8 字节就是一次野写。
- 于是加了 `SAFEFED`（只喂 `48+payload+8`，不喂 padding/65537 两坨）：WQI=4 与 WQI=5 **都不崩**，但 `readv=0 errno=0`、`testDatum` 未变 ⇒
  说明 SAFEFED 下拷贝根本没走完（管道被读空/提前 EOF），自改写没被触发 ⇒ **"要不要喂那 69 KB"不是可省的细节，它是机制的一部分**（su98 靠它把游标推到被改写的描述符上）。

  `wait.c:209-213` 只有 `WQ_FLAG_EXCLUSIVE` 才 `__add_wait_queue_tail`，而 binder 的 `wait_event_freezable` 非独占）⇒ **作废**，`clobber_data` 才是活路。
